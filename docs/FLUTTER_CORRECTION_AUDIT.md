## Material findings and corrections

1. **Platform mismatch:** existing `frontend/` is React/Vite; none of the 135 returned PR change sets contains Flutter implementation. 35 PRs change legacy frontend paths. P09-W01–W03's prior React completion claims do not complete their Flutter equivalents. P1/P2/P3/P5/P6/P7 UI-bearing requirements must also be reopened for Flutter; this is not just a P9 styling change.
2. **Competing authority:** repo master docs claimed sole authority over 16 phases and excluded native Flutter or called iOS native optional. Notion's hard gate, P0–P21 amendments and Figma Flutter handoff supersede them. Correction banners and repository agent rules now make this explicit while preserving original technical/history content.
3. **Registry arithmetic:** the final Notion registry contains **132 distinct planned PR entries**, not its stale stated total of 192. Its ten consolidated Phase 5 PRs allocate 65 real P05 work items. Across the registry, **157 distinct work-item IDs** are allocated; `P05-W46` is expressly absent and is not invented. Planned IDs are not GitHub PR numbers. The stale sentence proposing risk PR11 onward conflicts with the later authoritative ten-PR allocation and must not drive implementation.
4. **False evidence equivalence:** React/Vite builds, mobile metadata, Chromium viewports, axe and HTTP fixtures do not validate Flutter or native Android/iOS. Backend-only CI remains valuable. UI-level historical VERIFIED claims must be qualified by technology and scope; P4's explicitly non-visual backend/research contract can be retained without pretending a Flutter drawer was rendered.
5. **Native session/lifecycle gap:** production security is still a shared development operator-key baseline (`ROLE_OPERATOR`), not P10 user/account/role/session completion. Flutter web cookie/CSRF and native secure-session/refresh/logout behavior need separate contracts. Phone backgrounding, resume, network loss, expiry and UNKNOWN reconciliation require actual platform tests; a browser resize cannot substitute.
6. **Route/feature parity gap:** the current React router does not itself implement every expanded route contract (for example dedicated scenarios, news, account-readiness and backtest detail aliases). New Flutter routing must inventory supported APIs and deep links rather than mechanically copy 15 existing route surfaces. P21 Control/Learning/Trade Intelligence/Cost centers are not established by a legacy overview screen.
7. **P16–P21 remain in scope:** point-in-time ML datasets, model inference/calibration, SHAP attribution, MLflow governance and exposure-aware workload lifecycle are not proven by existing news adapters, deterministic scenarios or basic Terraform. Do not delete these six workstreams when reconciling repo plans. They need appropriate Java/Python/backend work and Flutter consumers; they do not require rewriting algorithms into Dart.
8. **Deployment/release gap:** existing workflows build the legacy React image and retain separately blocked AWS-region/account assumptions. This correction adds an explicit Flutter release lock before validation and before AWS credential acquisition in both deployment workflows. It does not run deployment, provision infrastructure, change OIDC trust or activate LIVE. The policy check is intentionally named as policy, not platform acceptance.
9. **Visual scope:** canonical Flutter design tokens, both `neonFuturisticAi`/`cleanModern`, light/dark/system, layout/semantics and real assets require implementation-specific verification. The existence of 176 Figma roots does not establish pixel parity. Existing React screenshots do not close that gap.

## Enforced correction and next work

`AGENTS.md`, the three repository master/risk documents and the [accepted delivery architecture](architecture/flutter-delivery.md) now identify the actual target. `scripts/check_flutter_delivery.py` rejects new legacy React UI changes, removal of required platforms, unsupported VERIFIED claims and incomplete Flutter foundation/CI structure. Its five policy tests exercise those negative paths. The policy passes backend-only work without pretending the Flutter client exists.

Both deployment workflows invoke `--require-complete` before AWS access. This initial correction deliberately has **no automatic release-unlock path**: it fails until replaced by a reviewed gate that verifies actual three-platform build/runtime artifacts and release acceptance. A green correction-policy PR cannot release the app. Repository branch protection settings are not changed by adding a workflow; making the policy a server-required PR check remains a separate repository-settings task.

The next implementation is FC-02/FC-03: real Flutter foundation plus one read-only operations-health slice on web, Android and iOS, before broad migration. The current unmerged React analytics work is parked, not counted and not submitted as a Flutter implementation. No backend/API/database work is deleted, no new React UI is merged by this correction, and no production cutover/LIVE activation is authorized.
