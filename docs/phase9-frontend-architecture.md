# P09-W01 frontend architecture

`App.jsx` is the sole route declaration. `/research/candidates/:candidateId`, `/operations`, `/notifications` and `/audit` join the existing research, portfolio, approvals and settings routes. Sidebar and mobile drawer expose the new operator destinations; breadcrumbs retain the research parent for candidate deep links.

Page controllers own queries, mutation state, filters, pagination and downloads. `ExperienceBoundary` selects presentation without a keyed route, query-client replacement or auth changes. Both selections use the same view component type with a presentation prop so local view state also survives. Views receive data/callbacks and do not import API clients. The shared operator query includes route parameters and authorization state, never the selected experience.

New routes are functional baseline compositions using existing semantic UI components. Operations displays source timestamps, unknown states and authoritative stop/mode evidence. Notifications expose active/history paging and authenticated acknowledgement, with duplicate-click prevention and explicit unchanged execution controls. Audit exposes exact server filters, payload details rendered as text and protected CSV downloads. Candidate history uses the persisted numeric candidate identity, preserves the research-only label and offers no execution action. The scanner API adds `candidateId` from the persisted row so this deep link is usable; fingerprint and instrument ID are not substituted for candidate identity. Scanner prices now use the server's referencePrice/suggestedStop/suggestedTarget fields.

The candidate detail baseline shows existing evaluation history. Full scenario charts, provenance drawer and evaluation launch belong to the subsequent inventory/controller work; an empty evaluation list is not presented as proof of candidate existence. Its reference context was inspected. This architecture PR does not claim pixel parity, complete four-appearance coverage or completion of P09-W02–W09. Their token, composition, screen-inventory, state, switching, responsive, accessibility and full E2E allocations remain open.

Playwright uses deterministic HTTP fixtures in both Pro desktop and Clear mobile: route/auth/query-cache/form continuity across a presentation switch, audit export and text-safe payload display, notification acknowledgement, diagnostic state and candidate deep links. Existing approval confirmation/expiry/retry/blocked-execution tests run alongside these. Axe checks the audit route; the full accessibility matrix remains P09-W08. Real PostgreSQL API tests separately prove scanner identity and the Phase 8 operator journey. Browser fixtures are not evidence of a connected database.

Rollback removes these frontend routes/views and the additive candidateId projection; no schema migration or external provider connection is required. No deployment or LIVE activation is included.
